Session 11: Exception Handling

Things go wrong: a user types letters where a number is expected, a file is missing, a number is divided by zero. Without handling, your program prints a stack trace and dies. Exception handling lets you catch the failure, respond sensibly, and keep running.

🧠 Memory Booster: Flashback
  • Reading a stack trace (S4): Exception in thread "main" ... at File.java:12 — kind of problem, then the line to open. Today you handle these instead of letting them crash the program.
  • Common exceptions you've met: ArithmeticException (÷0), NullPointerException, ArrayIndexOutOfBoundsException, NumberFormatException, InputMismatchException.
  • Inheritance (S9): every exception type is a subclass of Throwable. Catching a superclass catches its subclasses too.

1. What & Why

An exception is an object Java creates when something goes wrong at run time. If nothing "catches" it, it propagates up the call stack; reaching main uncaught, it prints a stack trace and the program stops.

🪂 Analogy: a fire drill, not a fire

A crash is a building burning down. An exception is the smoke alarm: it interrupts normal activity and routes everyone to a planned response (the catch block). Handled well, the building is fine and work resumes.

2. The Exception Hierarchy

Type tree
Throwable
├── Error              (serious JVM problems — OutOfMemoryError, StackOverflowError; don't catch these)
└── Exception
    ├── RuntimeException        UNCHECKED  (NullPointerException, ArithmeticException,
    │                                       IllegalArgumentException, IndexOutOfBoundsException, ...)
    └── (everything else)       CHECKED    (IOException, SQLException, your custom ones, ...)

Catching a type also catches all its subclasses. catch (Exception e) catches almost everything — usually too broad (see best practices).

3. Checked vs. Unchecked

4. try / catch

Java
try {
    int n = Integer.parseInt(userText);   // may throw NumberFormatException
    System.out.println("Doubled: " + (n * 2));
} catch (NumberFormatException e) {
    System.out.println("That wasn't a whole number.");
}
// execution continues here whether or not the exception happened

When the try body throws, Java immediately jumps to a matching catch — the rest of the try is skipped. The exception object e carries a message (e.getMessage()) and the trace (e.printStackTrace()).

5. Multiple catch & Multi-catch

Java
try {
    process(input);
} catch (NumberFormatException e) {          // most specific first
    System.out.println("bad number");
} catch (NullPointerException e) {
    System.out.println("missing value");
} catch (Exception e) {                       // catch-all last
    System.out.println("something else: " + e.getMessage());
}

// Multi-catch: same handling for several types
try {
    risky();
} catch (NumberFormatException | NullPointerException e) {
    System.out.println("input problem: " + e.getMessage());
}
⚠️ Order matters

A catch for a superclass must come after its subclasses. catch (Exception e) before catch (NumberFormatException e) is a compile error — the second could never be reached.

6. finally

A finally block runs no matter what — after a normal try, after a caught exception, even after a return. Use it for cleanup that must always happen.

JavaExceptionBasics.java (excerpt)
static int safeDivide(int a, int b) {
    try {
        return a / b;                 // 10/0 throws here
    } catch (ArithmeticException e) {
        System.out.println("catch: " + e.getMessage());   // "/ by zero"
        return 0;
    } finally {
        System.out.println("finally: always runs");        // prints in BOTH cases
    }
}

7. try-with-resources

Anything that implements AutoCloseable (files, streams, database connections, Scanner) can be opened in the try (...) header. Java calls its close() automatically when the block ends — success or exception — so you never leak a resource.

Java
try (Scanner file = new Scanner(new File("data.txt"))) {
    while (file.hasNextLine()) {
        System.out.println(file.nextLine());
    }
} catch (IOException e) {
    System.out.println("Could not read file: " + e.getMessage());
}
// file.close() was called for you — even if an exception was thrown

This is far safer than a manual finally { file.close(); }, which is easy to forget and awkward when close() itself can throw.

8. throw & throws

  • throw (statement) — raise an exception now: throw new IllegalArgumentException("age must be >= 0");
  • throws (method clause) — declare that a method might let a checked exception escape: void load() throws IOException { ... }
Java
static int parsePositive(String s) {
    int n = Integer.parseInt(s);              // may throw NumberFormatException (unchecked)
    if (n < 0) {
        throw new IllegalArgumentException("must be non-negative, got " + n);
    }
    return n;
}
💡 Fail fast on bad arguments

Validate a method's inputs at the top and throw new IllegalArgumentException immediately. A clear exception at the call site beats a mysterious NullPointerException ten methods deep.

9. Custom Exceptions

Define your own type when you want callers to catch your specific failure. Extend Exception for a checked one, or RuntimeException for unchecked.

JavaBankErrors.java (excerpt)
class InsufficientFundsException extends Exception {     // checked
    InsufficientFundsException(String message) { super(message); }
}

class Account {
    private double balance;

    void withdraw(double amount) throws InsufficientFundsException {
        if (amount > balance) {
            throw new InsufficientFundsException(
                String.format("need $%.2f but balance is $%.2f", amount, balance));
        }
        balance -= amount;
    }
}

// caller:
try {
    acc.withdraw(200);
} catch (InsufficientFundsException e) {
    System.out.println("declined: " + e.getMessage());
}

10. Best Practices

  • Catch specific types, not a bare Exception, so you don't accidentally swallow bugs.
  • Never leave a catch block empty. At minimum log it. Silently ignored exceptions are the worst kind of bug.
  • Don't use exceptions for normal flow. Checking if (index < array.length) beats catching ArrayIndexOutOfBoundsException.
  • Handle where you can actually respond. If a method can't recover, let the exception propagate to a caller that can.
  • Preserve the cause when re-throwing: throw new AppException("load failed", e);.
  • Prefer try-with-resources over manual finally cleanup.
  • Validate inputs early with IllegalArgumentException / IllegalStateException.

11. Executive Quick-Recap & Cheat Sheet

⚡ The 30-Second Mental Model

An exception unwinds the call stack until something catches it (or it crashes main). Checked exceptions must be caught or declared throws; unchecked (RuntimeException) need not be. try runs the risky code, catch handles a type (specific first), finally always runs, try-with-resources auto-closes. throw raises one; custom exceptions extend Exception or RuntimeException.

Core Syntax at a Glance

Java Cheat Sheet
class OutOfStockException extends Exception {
    OutOfStockException(String m) { super(m); }
}

static void buy(int stock, int qty) throws OutOfStockException {
    if (qty <= 0) throw new IllegalArgumentException("qty must be positive");   // unchecked
    if (qty > stock) throw new OutOfStockException("only " + stock + " left");   // checked
    System.out.println("sold " + qty);
}

public static void main(String[] args) {
    try {
        buy(3, 5);
    } catch (OutOfStockException e) {
        System.out.println("sorry: " + e.getMessage());
    } catch (IllegalArgumentException e) {
        System.out.println("bad request: " + e.getMessage());
    } finally {
        System.out.println("transaction attempt logged");
    }
}

Plain-English Glossary

Exception

An object representing a runtime problem; unwinds the stack until caught.

Checked

Must be caught or declared with throws; for expected external failures.

Unchecked

Subclass of RuntimeException; handling optional; usually a bug.

try / catch

Run risky code; on a matching exception, jump to the handler.

finally

A block that always runs — cleanup that must happen no matter what.

try-with-resources

try (Resource r = ...) — auto-calls r.close() at the end.

throw

Statement that raises an exception now.

throws

Method clause declaring a checked exception may escape.

Custom exception

Your own class extending Exception (checked) or RuntimeException (unchecked).

Stack trace

The chain of method calls an uncaught exception prints; read top-down.

❓ Q1: Does a finally block run if the try block executes return?
Answer: Yes. finally runs before the method actually returns — it always runs (barring System.exit or a JVM crash).
❓ Q2: The compiler forces you to handle which kind of exception?
Answer: Checked exceptions (subclasses of Exception but not RuntimeException) — catch them or add throws. Unchecked ones are optional.
❓ Q3: Why must catch (NumberFormatException e) come before catch (Exception e)?
Answer: Exception is a superclass and would catch everything first, making the specific block unreachable — a compile error.
❓ Q4: What does try-with-resources save you from writing?
Answer: A manual finally { resource.close(); } — it calls close() automatically, even on exception.
